## 2. GitHub Environment 审批配置

### 2.1 实时状态


| 项                        | 结果                   |
| ------------------------- | ---------------------- |

| Required Reviewers 已配置 | **否**                 |
| 审批人身份可核验          | **否**（没有环境可读） |

当前自动化身份对仓库有 `admin: true`，**因此技术上可以创建该 Environment**；但本轮未获
授权，**没有创建或修改任何环境设置**。

### 2.2 代码层的 Fail Closed（已存在且已验证）

- `.github/workflows/publish-dev.yml` 只有 `workflow_dispatch`，没有 push/tag/schedule 触发。
- `authorize` job **在**审批 job 之前运行，调用
  `release-transaction.mjs environment-gate --environment dev-pre-release`；
  HTTP 403/404/不可读 → `unverified` → `authorize-publish` 拒绝。
- 审批后的 `publish` job 再次运行 `authorize-publish`，且 `publish-draft` 内部**第三次**
  重新判定；三次读取同一份 job-level env。
- 本地无授权实跑：`exit 1`，六条独立拒绝（缺 dispatch、缺 publish 输入、短语不匹配、
  TagCommitSHA 无效、环境未验证、拒绝写入）。

**结论：`PUBLISH_FAIL_CLOSED = PASS`（代码层），`ENVIRONMENT_EXISTS = BLOCKED`（仓库设置）。**

### 2.3 维护者需要完成的精确步骤

`Settings → Environments → New environment`：

1. 名称必须是 **`dev-pre-release`**（大小写与连字符完全一致）。
2. 勾选 **Required reviewers**，添加至少一名实际维护者账号。
3. 勾选 **Prevent self-review**，使触发 workflow 的人不能批准自己的运行。
4. 若界面提供 **Allow administrators to bypass configured protection rules**，**关闭**它。
5. （建议）在 Deployment branches 中只允许 `main`。
6. 保存后，用只读命令确认：

```bash
gh api repos/baicie/todo/environments --jq '.environments[].name'
gh api repos/baicie/todo/environments/dev-pre-release \
  --jq '.protection_rules[] | select(.type=="required_reviewers") | {type,reviewers,prevent_self_review}'
```

### 2.4 Environment 保护规则核验（三项缺一不可）

只读命令能读到什么，才算什么；读不到一律按未配置处理，不得推断为通过。

| 检查项                             | 读取字段                                              | 当前值                     | 判定        |
| ---------------------------------- | ----------------------------------------------------- | -------------------------- | ----------- |
| Environment `dev-pre-release` 存在 | `GET /environments`                                   | `total_count: 0`，单项 404 | BLOCKED     |
| Required Reviewers ≥ 1             | `protection_rules[type=required_reviewers].reviewers` | 无环境可读                 | BLOCKED     |
| Prevent self-review 已开启         | 同上规则的 `prevent_self_review`                      | 无环境可读                 | BLOCKED     |
| 管理员不得绕过                     | 环境对象的 `can_admins_bypass`                        | 无环境可读                 | BLOCKED     |
| **发布审批策略完整**               | 以上四项全部满足                                      | —                          | **BLOCKED** |

Environment 配置完成后，用下面两条命令做**断言式**核验（非零退出即不合格）：

```bash
env_json=$(gh api repos/baicie/todo/environments/dev-pre-release)

# 1) 至少一名 reviewer，且禁止自我审批
echo "$env_json" | jq -e '
  [.protection_rules[] | select(.type == "required_reviewers")] as $rules
  | ($rules | length) == 1
    and ($rules[0].reviewers | length) >= 1
    and ($rules[0].prevent_self_review == true)
'

# 2) 管理员不能绕过保护规则
echo "$env_json" | jq -e '.can_admins_bypass == false'
```

如果某个字段在 API 响应里不存在（不同 GitHub 版本字段可能不同），**不得**把它当作通过；
应回到 UI 确认，并在报告中记录为未核验。

### 2.5 需要明确记录的残余风险

`release-transaction.mjs` 的环境门禁只检查 **存在 `required_reviewers` 且至少一名 reviewer**；
它**不读取** `prevent_self_review`，也**不读取** `can_admins_bypass`。也就是说：

- 如果维护者在界面上允许管理员绕过保护规则，代码门禁仍会打印 `enforced`；
- 如果未开启 Prevent self-review，触发者可能批准自己的运行。

这两项是 GitHub 设置，工作流无法证明；必须在 §2.3 的步骤 3、4 中人工关闭，并在
Environment 配置完成后用上面的只读命令复核。

### 最终回答

1. **现在可以创建 `0.0.1-dev.1` Tag 吗？**
   技术上可以：源已冻结、无冲突、staging 只产 draft。但**未获操作授权**，本轮不得执行。

2. **Draft Staging 是否存在代码或配置阻断？**
   没有代码阻断。`release-dev` 不读取 `dev-pre-release`，因此 Environment 缺失不阻塞
   staging。唯一非代码风险是构建时间长与 draft 清理。

3. **公开发布缺少哪些条件？**
   - `dev-pre-release` Environment 与 Required Reviewers（含关闭 self-review 与管理员绕过）；
   - 五项桌面 QA（安装、IPC、通知中心、横幅、点击）仍为 NOT_RUN；
   - 维护者 dispatch `publish-dev` 并完成人工审批。

4. **哪些工作必须由维护者亲自操作？**
   配置 Environment；批准是否 staging；创建/推送 tag；dispatch publish；在 Actions 页面
   批准部署；在真实桌面完成通知验收。

5. **若现在就创建 Draft，潜在风险与副作用？**
   触发六端构建（耗时、消耗 Actions 配额）；在 Releases 页留下一个 draft；tag 一旦推送即
   指向 `496015a`，删除 tag 属于额外未授权操作且可能留下孤立 draft；若构建失败会留下
   partial draft，需要人工清理。

6. **是否推荐进入 Draft Staging？**
   **推荐先配置 Environment，再执行 staging。** 若维护者接受上述副作用，staging 本身是
   可回退的（draft 不对公众可见）；但在桌面 QA 与审批配置完成前，**不建议公开发布**。
