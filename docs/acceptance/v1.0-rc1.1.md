## 1. Phase A：同步会话生命周期

### 已确认风险

- `runInFlight` 只合并并发调用，登出/清库/账号切换可以绕过它。
- 旧会话迟到的 `syncApplyResult()` 仍可能把 shadow、cursor 和任务写回正在清理或新账号的数据库。
- 旧请求完成后可能重新设置 `phase=connected`、`synced` 或 `persist(true)`。
- 401 刷新和 `forceBootstrap` 没有 generation 隔离。

### 修复

- `apps/app/src/sync/cloud.ts`
  - 引入 `sessionGeneration` / `sessionToken` / `disposed`。
  - `beginSession()` 生成 token；`invalidateSession()` 立即递增 generation、清空 token、停止 timer/lifecycle 回调、丢弃旧 engine/run promise。
  - 每次 `executeSync()` 捕获 generation，在所有 await 后校验；`onEngineState` 绑定 generation。
  - `signOut()` 先失效 fence，再写 `syncSession=null`、撤销服务端会话、清 token，最后清库/解绑。
  - `dispose()` 同样使旧 generation 失效。
  - 401 最多刷新一次；刷新失败进入 `expired`，不无限重试。
- `apps/app/src/sync/storage.ts`
  - `CloudSyncStorage` 增加 `syncSetSession()`；`syncApplyResult` / `syncReplaceSnapshot` 接受 session id。
  - 新增 `StaleSyncSessionError`。
- Web `DexieTaskRepository`：在 `syncApplyResult` / `syncReplaceSnapshot` / `syncInitializeCloud` 的事务内读取 `syncSession`，不匹配即抛错；`clearAll` 删除 fence。
- Native `TodoStore`：`kv_state.sync_session`；`apply_server_result` / `sync_replace_snapshot_fenced` / `sync_initialize_cloud` 在 SQLite 事务内校验 session；`clear_all` 删除 fence；新增 `STALE_SYNC_SESSION` 错误码。
- Tauri adapter 通过 `sessionId` 传递 fence，并把原生错误映射为 `StaleSyncSessionError`。

### 测试

`apps/app/src/sync/cloud-lifecycle.test.ts`：

1. HTTP 响应延迟期间 `signOut(true)`，late response 不得重建任务，outbox/cursor 保持清空。
2. 延迟期间 `dispose()`，late response 不得落库。
3. 401 -> refresh 成功 -> `synced`。
4. 第二次 401 -> `auth-required`/expired，不能显示 synced。
5. 账号 A 延迟响应 + 账号 B 新 session，旧响应不得覆盖 B。
6. stale bootstrap snapshot 被 DB fence 拒绝。
7. `sync` 与 `forceBootstrap` 并发：force bootstrap 等待在途 sync 完成后再安装快照，最终 cursor 不回退、迟到 sync 不覆盖 bootstrap。

`apps/app/src/adapters/web-repository.test.ts`：

- stale `syncReplaceSnapshot` 拒绝，已有任务不变。

## 7. PR #1 复审修复（基线 `6313d8b`）

### Blocking 1：Session fence 异步清除竞态

**根因**

- `invalidateSession()` 发出未等待的 `syncSetSession(null)`；它可能在 `beginSession()` 安装新 token 之后才完成，从而清掉新 session。
- `beginSession()` 在 `await` 后读取当前 `sessionGeneration`，并发 begin/invalidate 时 token 与 generation 可能错配。

**修复**

- `beginSession()` 在 await 前捕获 `generation`，await 后同时校验 generation、token 和 disposed；不匹配抛 `StaleSyncSessionError`。
- 新增串行 fence 队列；同一个 controller 内 begin/clear 按调用顺序执行，被更新 generation 取代的写入直接跳过。
- 新增 `syncClearSession(expectedToken)`，Web Dexie 与 Native SQLite 都在**写事务内比较 expectedToken** 后才删除；旧会话迟到 clear 对后继 token 是无操作。
- Tauri 新增 `sync_clear_session` action；`clearAll` 继续无条件删除。
- `signOut()` await fence clear 后再清本地数据；`dispose()` 也保留最终 clear。

**新增故障注入测试**

- `does not let a superseded session clear a newer fence`：旧 clear 被挂起、新 session 已开始且其 HTTP 响应也在途；释放旧 clear 后断言新任务仍成功落库。
- `rejects a stale beginSession after a newer initialize supersedes it`：第一次 token 写入被延迟，第二次 initialize 超越；旧 begin 必须失败，最终状态属于新 session。
- Web `does not let an old session clear a newer fence token` 与 Native `stale_sync_session_clear_cannot_remove_a_newer_token` 在 DB 事务层验证条件删除。

### Blocking 2：forceBootstrap 完整互斥

**根因**

- 旧实现只等待当时已有的 `runInFlight`；在 snapshot 下载/替换窗口里，online/poll/subscribe/manual 仍可启动新的 sync 并交错，可能回退 cursor。

**修复**

- 引入 `bootstrapInFlight` / `bootstrapCompletion` / `queuedSync`。
- bootstrap 的“等待旧 sync → 下载 snapshot → 事务替换 → cursor 诊断 → 随后一次增量 sync”成为互斥链路。
- bootstrap 期间的任何新 sync 触发只登记一个 `queuedSync`，在 snapshot 安装后串行执行；重复 bootstrap 调用复用同一个 completion。
- generation 失效时 queued sync 不会落到新 session。

**新增乱序测试**

- `defers a new sync request until bootstrap snapshot and cursor are installed`：挂起 bootstrap 下载，触发 manual sync，断言 bootstrap 完成前没有第二个 `/sync` 请求；完成后请求 cursor 为 `9`，最终 cursor `10`，bootstrap 与增量任务同时存在，outbox 为 0。

### Blocking 3：iOS 空备注幂等性

**根因**

- Rust 用原始空串作为指纹，但 iOS 把空正文替换成显示文案“该完成这项任务了”，`list()` 又返回该显示文案；第二次 reconcile 因此永远判定 body 变化并反复取消/重建。

**修复**

- iOS `schedule()` 将 `rawTitle` / `rawBody` 写入 `userInfo`，显示文案只用于 `UNMutableNotificationContent`。
- iOS `list()` 优先读 `userInfo` 原始值；旧 pending 请求没有原始字段时，把显示 fallback 规范化为空串。
- Rust 增加 `body_matches()`：空备注接受空串或 iOS 显示 fallback；非空备注严格要求原始正文。旧 iOS 队列即使尚未重建也不会误判。
- Android 本来持久化原始 body/title/fireAt；Windows/桌面队列保存原始值。Rust 时间比较使用解析后的 instant，新增 `Z` 与 `+00:00` 等价断言。

**新增测试**

- `repeated_reconcile_does_not_reschedule_unchanged_empty_body_reminders`：第一次 scheduled=2，第二次 scheduled=0、unchanged=2、schedule_calls 仍为 2。
- `ios_default_body_is_treated_as_empty_raw_body`：预置 iOS 显示 fallback 的系统条目，空备注任务必须 unchanged，而不是重新调度。
- `changed_raw_body_is_the_only_body_fingerprint_change` 与权限拒绝路径覆盖。

**剩余风险**：本机无 Xcode/Swift 工具链，iOS 源码修改未编译、未真机验证；Android/Windows 无真机。上述平台状态仍为 `NOT_RUN`，不声称平台运行通过。
