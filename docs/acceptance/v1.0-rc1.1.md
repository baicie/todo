## 1. Phase A：同步会话生命周期

### 已确认风险

- `runInFlight` 只合并并发调用，登出/清库/账号切换可以绕过它。
- 旧会话迟到的 `syncApplyResult()` 仍可能把 shadow、cursor 和任务写回正在清理或新账号的数据库。
- 旧请求完成后可能重新设置 `phase=connected`、`synced` 或 `persist(true)`。
- 401 刷新和 `forceBootstrap` 没有 generation 隔离。

### 修复

- `apps/app/src/sync/cloud.ts`
  - 引入 `sessionGeneration` / `sessionToken` / `disposed`。
  - `beginSession()` 生成 token；`invalidateSession()` 立即递增 generation、清空 token、停止 timer/lifecycle 回调、丢弃旧 engine/run promise。
  - 每次 `executeSync()` 捕获 generation，在所有 await 后校验；`onEngineState` 绑定 generation。
  - `signOut()` 先失效 fence，再写 `syncSession=null`、撤销服务端会话、清 token，最后清库/解绑。
  - `dispose()` 同样使旧 generation 失效。
  - 401 最多刷新一次；刷新失败进入 `expired`，不无限重试。
- `apps/app/src/sync/storage.ts`
  - `CloudSyncStorage` 增加 `syncSetSession()`；`syncApplyResult` / `syncReplaceSnapshot` 接受 session id。
  - 新增 `StaleSyncSessionError`。
- Web `DexieTaskRepository`：在 `syncApplyResult` / `syncReplaceSnapshot` / `syncInitializeCloud` 的事务内读取 `syncSession`，不匹配即抛错；`clearAll` 删除 fence。
- Native `TodoStore`：`kv_state.sync_session`；`apply_server_result` / `sync_replace_snapshot_fenced` / `sync_initialize_cloud` 在 SQLite 事务内校验 session；`clear_all` 删除 fence；新增 `STALE_SYNC_SESSION` 错误码。
- Tauri adapter 通过 `sessionId` 传递 fence，并把原生错误映射为 `StaleSyncSessionError`。

### 测试

`apps/app/src/sync/cloud-lifecycle.test.ts`：

1. HTTP 响应延迟期间 `signOut(true)`，late response 不得重建任务，outbox/cursor 保持清空。
2. 延迟期间 `dispose()`，late response 不得落库。
3. 401 -> refresh 成功 -> `synced`。
4. 第二次 401 -> `auth-required`/expired，不能显示 synced。
5. 账号 A 延迟响应 + 账号 B 新 session，旧响应不得覆盖 B。
6. stale bootstrap snapshot 被 DB fence 拒绝。
7. `sync` 与 `forceBootstrap` 并发：force bootstrap 等待在途 sync 完成后再安装快照，最终 cursor 不回退、迟到 sync 不覆盖 bootstrap。

`apps/app/src/adapters/web-repository.test.ts`：

- stale `syncApplyResult` 拒绝，cursor/outbox 保留。
- stale `syncReplaceSnapshot` 拒绝，已有任务不变。
- stale `syncInitializeCloud` 拒绝，登录/合并快照不得写回旧 session。
- `clearAll` 后旧 apply 拒绝，数据库为空。

`crates/native-core/tests/repository.rs`：

- `stale_sync_session_cannot_commit_server_results`
- `stale_sync_session_cannot_replace_a_snapshot`
- `stale_sync_session_cannot_initialize_cloud_data`

## 2. Phase B：Native 提醒系统队列对账

### 已确认风险

- Tauri 启动只靠 WebView 内 Map，未真正调用原生 `reschedule_reminders()`。
- Native 命令每次清空全部通知，再重建；失败只记录日志。
- Rust `ReminderReconcileReport` 未回传应用层。
- iOS 64 条容量与 30 天窗口没有结构化报告。

### 修复

- `apps/app/src/App.tsx`：Tauri 分支改为调用 `rescheduleUpcoming()`，将 `failed/permissionDenied/outsideWindow/capacityExceeded` 转为可见 `ReminderIssue`，不再维护 WebView 作为 Tauri 的事实来源。
- `packages/application/src/ports.ts`：新增 `ReminderReconcileReport`，`rescheduleUpcoming()` 返回结构化报告。
- `apps/native/src-tauri/src/reminders.rs`：
  - `ScheduledReminderInfo` 暴露系统队列快照。
  - `scheduled()` 供 Rust 对账；桌面队列与移动插件均实现。
- `apps/native/src-tauri/src/commands.rs`：
  - `reschedule_reminders()` 返回 `ReminderReconcileReport`，包含 scheduled/cancelled/unchanged/skippedPast/outsideWindow/capacityExceeded/permissionDenied/failed。
  - 先取消不再存在于 SQLite 的系统通知；对指纹一致的条目直接 `unchanged`，不重复取消/重建。
  - 权限未授予时返回 `permissionDenied`，不声称调度成功。
  - 超出窗口/容量时取消旧通知并报告。
- iOS 插件既有的 30 天窗口和 64 条 pending 限制保留；Rust 将 pending limit 错误映射为 `capacity-exceeded`。调度顺序按 SQLite `remind_at` 升序，容量内优先最近提醒。

### 测试/测量

- 1001 条 Web 提醒查询：单次 indexed query 约 **10–14 ms**（jsdom，测试环境；最近一次 12.77 ms）。
- 1001 条未变化提醒 reconcile：约 **1–2 ms**，`schedule` 调用 **0** 次（最近一次 2.0 ms）。
- 1001 条 Native SQLite 查询：约 **5.30 ms**（in-memory SQLite）。
- `reminder_query_handles_more_than_one_thousand_entries`：1001 条，无截断。
- Tauri 对账 IPC 固定为 **1 次/reschedule**；单任务失败不再是 console-only。
- 100k 任务与真实设备 IPC 时延：**NOT_RUN**（无基准环境/设备）。
