## D. Native Retry State Machine

**修复前（`main`）**：`DeliveryMeta.requeue_used: bool` 是整个 listener 生命周期的单一标志。

```text
A -> S1 in flight -> reload S2：requeue_used=false -> requeue A，置 true
A -> S2 in flight -> reload S3：requeue_used=true -> A ACTIVATION_EXPIRED（正确），但标志仍为 true
B -> S3 in flight -> reload S4：requeue_used=true -> B 被 EXPIRED（错误，B 失去自己的首次重试）
```

**修复后**：重试预算属于单条 activation（`#[serde(skip)] ActivationMeta { attempts, requeues_used, enqueued_at }`），
`MAX_REQUEUES_PER_ACTIVATION = 1`、`MAX_DELIVERY_ATTEMPTS = 2`，共享状态不再持有任何重试标志。
`ACTIVATION_EXPIRED` 安全机制保留（同一 activation 第二次 reload 仍过期），只是不再污染其它 activation。

交付生命周期（每条 activation 独立）：

```text
PENDING -> DELIVERING(reserved) -> IN_FLIGHT
        -> { ACK_OPENED, ACK_REJECTED, ACK_EXPIRED, RETRY_PENDING -> IN_FLIGHT } -> TERMINAL
```

WebView JSON 契约不变：`activation_json_contract_is_stable` 断言序列化键恰为
`activationId` / `target` / `taskTitle`，`meta` 被 `serde(skip)` 排除。

## E. Concurrency / Queue Ownership

**修复前**：`take_for_listener` 先 pop，再在另一把锁里重新检查；session 变化时只有
`pending.len() < 8` 才回队，否则 activation **无终态、无证据地消失**。

**修复后（所有权转移事务）**：

1. **单锁**：`NotificationActivationState { state: Mutex<DeliveryState>, sequence: AtomicU64 }`，
   `pending` / `reserved` / `in_flight` / `completed` / `acked` / `rejections` / `session_id` 同属一个锁。
   结论：**不存在锁顺序问题**（只有一把锁，无可嵌套的第二把）；`with_state` 内部不再调用 `self.` 方法。
2. **所有权转移**：在**同一个临界区**内 pop 并把 activation 移入 `reserved`；账号/任务校验
   （会触及账号注册表与 SQLite）在锁外执行；提交时若 ticket 仍是自己的则提升为 in flight，否则回队或记拒绝。
   由于槽位已记账，**回队不可能因容量失败**——这正是原缺陷的根因。
3. **RAII 守卫**：`ReservationGuard` 在提前返回或 panic 时归还 reservation；拿不到锁（poisoned）
   一律 fail closed（`Unavailable` / `Poisoned` / `false`），生产代码无 `unwrap()` / `expect(`。
4. **容量**：`ACTIVATION_CAPACITY = 8` 统计 `pending + reserved + in_flight`。新到达且已满时
   **淘汰最旧的 pending** 并记录可观测证据 `ACTIVATION_QUEUE_OVERFLOW`，**绝不覆盖 reserved / in_flight**，
   不再静默丢弃。代价：一条 activation 正在交付时 pending 最多 7 条（有界内存的正确语义）。
5. **不忙轮询**：drain 上限仍为 8；TTL 300s（可注入时钟）在 reserve / commit / restore / reload 处检查。

确定性证据（全部无 sleep）：

| 测试                                                                                                | 覆盖                                                                                                                                                                    |
| --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `concurrent_reload_and_enqueue_never_loses_or_duplicates_an_activation`                             | `std::thread::scope` + 双向 `Barrier`：A 校验的同时 B 替换 session、C 入队 8 条；断言恢复、恰好 1 条 overflow、4 条 `ACCOUNT_SWITCH_REQUIRED`、无跨账号、无重复、无死锁 |
| `session_change_during_validation_restores_the_activation_instead_of_dropping_it`                   | 缺陷 C 的确定性复现                                                                                                                                                     |
| `panicking_validation_restores_the_reserved_activation`                                             | panic 时守卫归还                                                                                                                                                        |
| `accounting_invariant_survives_every_transition` + `audit_helper_detects_an_unaccounted_activation` | 账本：每条 activation 要么在唯一活动槽位，要么有唯一终态记录；并有非空洞性证明                                                                                          |
| `randomized_state_machine_keeps_accounting_consistent`                                              | 400 步固定种子伪随机，每步后审计                                                                                                                                        |

## F. WebView Navigation / ACK Transaction

**修复前**：`getTask` -> `setSelectedTask` + `setSelectedId` -> 轮询
`document.querySelector('aside.detail .detail__title')` 10 次 50ms -> 失败即 ACK `rejected`，
即「UI 已切到目标任务，但交付被标记为拒绝」。

**修复后**：`apps/app/src/lib/task-navigation.ts` 事务层（无 DOM、无 timer、无框架依赖）：

```text
Task Loaded -> Account Validated -> Navigation Requested(generation G)
            -> Detail Rendered（视图通过 signal 报告 {taskId, generation}）
            -> Detail Confirmed（report.generation >= G）-> ACK opened
任何一步失败 / 被取代 / abort -> 回滚到上一次选择 -> ACK rejected
```

| 要求                              | 实现                                                                   |
| --------------------------------- | ---------------------------------------------------------------------- |
| 旧 Navigation 不覆盖新 Navigation | 每次尝试 `++generation`，旧事务立即 settle(false)                      |
| Account Switch 立即失效           | 提交前、确认回调、advance 后均重读 `activeAccountId()`                 |
| Abort 后不允许迟到提交            | 返回的 promise 与加载解耦，abort 立即 settle(false)，提交前再次检查    |
| Detail 不存在                     | `getTask` 返回 null => 不提交、不改变现有选择、返回 false              |
| DOM 未渲染不能提前 ACK            | ACK 只由视图渲染报告触发，无轮询、无固定延迟                           |
| DOM 已切换但验证失败              | 明确回滚：仅当本事务仍拥有视图时恢复上一次选择                         |
| ACK 失败不伪造成功                | bridge 只反映 `openTask` 真实结果，失败走 `rejected`                   |
| 页面卸载不修改 UI                 | `onCleanup` -> `notificationAbort.abort()` + `taskNavigator.dispose()` |
| 用户手动选择不被覆盖              | 视图报告其它 taskId 即视为被取代，且不抢回选择                         |

脆弱依赖消除：不再使用 `document.querySelector('aside.detail .detail__title')`，不再扩大轮询次数。
保留的 `OPEN_TASK_TIMEOUT_MS = 5000` 是既有**上界**而非确认机制，确认完全由渲染信号驱动，视为已接受的决策。

## G. Release Version & SHA Consistency

**修复前**：release job 用 `github.event.inputs.version`，而 web / macOS / Android 的资产命名用
`GITHUB_REF_NAME`。从分支手动触发时 `GITHUB_REF_NAME=main`，发布出 `Shishi-main-*` 资产挂在
`0.0.1-dev.0` 标签下；且没有任何步骤校验被构建的 commit 是否等于标签指向的 commit。

**修复后**：首个 `context` job 解析并校验唯一 Release Context，其余 job 全部消费其输出。

| 字段                              | 来源 / 约束                                                              |
| --------------------------------- | ------------------------------------------------------------------------ |
| `ReleaseVersion` / `ReleaseTag`   | 标签（push）或 `inputs.version`（dispatch），统一规范化                  |
| `TagCommitSHA` / `BuildCommitSHA` | 必须相等                                                                 |
| `AppVersion`                      | 取自 `tauri.dev.conf.json`（dev 覆盖 stable），必须等于 `ReleaseVersion` |
| `ArtifactVersion`                 | 必须等于 `ReleaseVersion`，且是唯一命名函数 `formatArtifactName` 的输入  |
| `ReleaseChannel`                  | 必须为 `dev@@（标签形如 `_-dev._`）                                      |

标签不存在 / 非 dev 标签 / 版本不一致 / commit 不一致 => **在任何构建开始前失败**。每个构建 job 以
`ref: needs.context.outputs.TagCommitSHA` 检出并再次断言 HEAD 等于标签提交。发布前
`verify-assets --stage pre` 校验 15 项资产存在且非空，写入 manifest（commit、tag、版本、通道、
rustc/node/pnpm/tauri-cli 版本、每个资产 size+sha256、run id），再 `--stage final` 校验 17 项资产哈希一致、
无悬空条目，最后才调用 pinned `softprops/action-gh-release`（`fail_on_unmatched_files`）。
平台身份在各自 job 内校验：Windows PE `ProductName`、macOS `lipo` 架构 + `CFBundleIdentifier`、
Android 每 ABI 的 `lib/<abi>/` + `aapt2 dump badging` 的 package id / versionName + AAB 清单字符串。
供应链：release 路径的第三方 Action 全部 pin 到 40 位 SHA（`scripts/release/actions.lock.json` 记录 tag+sha），
顶层 `permissions: contents: read`，仅发布 job 持有 `contents: write`。

本地已验证：`node --test` **33/33**；`lint-workflows` 输出「OK GitHub expressions: 4 workflow file(s) clean」；
实测 resolve 得到 `TagCommitSHA == refs/tags/0.0.1-dev.0^{commit}`（`db9e35a`）；
`9.9.9-dev.0`（标签不存在）、`v1.1.0-rc.1`（非 dev 通道）、分支 push 均被拒绝。
