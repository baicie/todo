## 2. QA 身份规范化

### 2.1 发现的问题

QA 身份被**复制粘贴到 8 处**，而 `tauri.qa.conf.json` 只是其中一处：

| 位置                                                           | 旧值                                 |
| -------------------------------------------------------------- | ------------------------------------ |
| `tauri.qa.conf.json`                                           | `Shishi QA RC2D` / `1.0.0-rc2d`      |
| `scripts/qa/native/harness-target.mjs`                         | `QA_PRODUCT_NAME = 'Shishi QA RC2D'` |
| `scripts/qa/native/qa-executable.mjs`                          | `QA_PRODUCT` + 两条安装根路径        |
| `scripts/qa/native/run-windows.ps1`                            | 安装根路径 + `ProductName` 硬门禁    |
| `scripts/qa/native/check-windows-activation-prerequisites.ps1` | 开始菜单快捷方式路径                 |
| `scripts/qa/native/windows-notification-diagnostic.ps1`        | 开始菜单快捷方式路径                 |
| `scripts/qa/native/bench.mjs`                                  | `appVersion: '1.0.0-rc2d'`           |
| `.github/workflows/native-qa.yml`                              | artifact `shishi-rc2d-qa-windows`    |

这不是命名不整齐的问题：只要改一处而漏掉另一处，harness 会**拒绝它刚被要求验证的那个包**
（`ProductName mismatch`），或者继续去上一个版本的安装目录找可执行文件——两种都是**静默失败**。

### 2.2 修复：单一事实来源

新增 `scripts/qa/native/qa-identity.mjs`，它**直接读取 `tauri.qa.conf.json`**，导出：

```text
QA_RELEASE_CANDIDATE     V1.1-RC1
QA_PRODUCT_NAME          Shishi QA V1.1-RC1     （= 配置 productName）
QA_PRODUCT_VERSION       1.1.0-rc1              （= 配置 version）
QA_IDENTIFIER            app.shishi.todo.qa     （= 配置 identifier）
QA_CREDENTIAL_SERVICE    app.shishi.todo.rc2d-qa.secure-token
QA_DATA_ROOT_DIRNAME     app.shishi.todo.qa
PRODUCTION_DATA_ROOT_DIRNAME  app.shishi.todo
qaInstallRoots(localAppData) / qaStartMenuShortcut(appData)
```

所有消费者改为导入它；两个 PowerShell 探针无法导入 ES module，改用
`node qa-identity.mjs --field productName` 取值，取不到就**抛错**而不是退回旧字面量。

### 2.3 改名边界：什么改了，什么没改

| 项目                    | 旧值                                   | 新值                 | 理由                                                       |
| ----------------------- | -------------------------------------- | -------------------- | ---------------------------------------------------------- |
| productName             | `Shishi QA RC2D`                       | `Shishi QA V1.1-RC1` | 显示名、NSIS 安装目录、卸载项；**随候选版本变化**          |
| version                 | `1.0.0-rc2d`                           | `1.1.0-rc1`          | 同上                                                       |
| identifier              | `app.shishi.todo.qa`                   | **不变**             | 安装/数据根/凭据/AUMID 命名空间，已有 QA 数据活在这里      |
| 凭据服务                | `app.shishi.todo.rc2d-qa.secure-token` | **不变**             | 与 identifier 解耦；改名会让既有 QA refresh token 全部失效 |
| Stable / Dev identifier | —                                      | **未改动**           | 任务明确要求不为统一名字动它们                             |

`Shishi QA RC2D` 安装在 `%LOCALAPPDATA%` 下的旧目录、旧卸载项、旧快捷方式**都不受影响**：
新包的安装目录名与卸载项随 productName 变化，NSIS 只删除自己的目录。

### 2.4 配置一致性契约测试（防止下个版本再次留下旧标识）

新增 `scripts/qa/native/qa-identity.test.mjs`，10 项：

1. 配置与派生常量一致（含窗口标题）；
2. 产品名以候选版本结尾，版本号编码候选版本（`V1.1-RC1` → `1.1.0-rc1`）；
3. 三通道的 identifier / 数据根 / 凭据服务互不相同，且 Rust 映射与 JS 常量一致；
4. 安装根与快捷方式跟随 productName，不跟随 identifier；
5. **六个隔离维度**（identifier、数据根、凭据服务、AUMID、安装目录、开始菜单）在 QA/Dev/Stable 之间两两不同，且 QA 安装目录不是 Dev/Stable 目录的子路径；
6. 六个消费者文件里不再有 `Shishi QA RC2D` / `1.0.0-rc2d` 字面量；
7. `run-windows.ps1` 通过 `qa-identity.mjs` 解析名字，且两处使用点都引用解析值；
8. Rust 打包契约仍在（见 §2.5）；
9. CI artifact 名带候选版本；
10. 对整个 `scripts/qa/native/` 目录做字面量扫描（防止新增消费者绕过清单）。

`apps/native/src-tauri/src/build_identity.rs` 新增
`qa_identity_survives_a_release_candidate_bump`：productName/version 随候选版本变，
identifier/数据根/凭据/AUMID 不变，且 QA 名必须保留 `Shishi QA ` 前缀——否则 harness 的
`ProductName` 门禁就可能接受一个生产包。

`qa-identity.test.mjs` 与 `qa-executable.test.mjs` 已加入 `pnpm test:qa-harness`，
而 `web.yml` 每次 PR 都跑该脚本，所以这条契约**在 CI 上生效**，不是本地约定。

`qa-executable.mjs` 在启动前就拒绝三类证据：QA 与生产数据根相同、启动前生产数据根已存在、
manifest HEAD/哈希不符。也就是说，**即使将来真机验收时数据根串了，harness 也会拒绝出报告**。

### 3.3 为什么本轮没有真机安装

本机不满足"可证明与真实数据隔离"：

- 已有三套安装在用：`Shishi Dev 0.0.1-dev.1`、`Shishi QA RC2D 1.0.0-rc2d`、
  `Shishi RC2C Validation 1.0.0-rc2c`，其中 Dev 与真实数据共存；
- 没有可用的独立 Windows VM，也没有专用 QA 测试账号
  （`Get-LocalUser` 只有主账号与系统内置账号）；
- 在主用户环境安装会创建新的开始菜单项、注册 AUMID、并可能改动通知设置，
  而任务明确要求"不得在当前主用户环境执行有数据覆盖风险的安装"。

因此安装类项目按任务要求保持 `NOT_RUN`，并给出可直接执行的 Runbook（§4）。

### 3.4 CI 首次运行发现的真实缺陷（`8ea38bb`）

把 `qa-executable.test.mjs` 接入 `test:qa-harness` 之后，这两个测试**第一次在 CI 的
Linux runner 上真正执行**，并立即失败：

```text
✖ rejects executable outside allowed QA roots
✖ rejects junction escape from allowed root
```

根因不是新代码，而是 `qa-executable.mjs` 的 `inside()`：

```js
return rel !== '' && rel !== '..' && !rel.startsWith(`..\\`) && !isAbsolute(rel);
```

`path.relative()` 使用**宿主分隔符**；在 Linux 上逃逸是 `../x`，而判断只匹配 Windows 的
`..\x`。于是前缀测试永远不成立，**任何路径都被判为「在允许根之内」**——那个用来阻止 QA
harness 启动非 QA 目录二进制的门禁，在跑 CI 的平台上等于关闭。

修复：把分隔符作为参数（`isContained(rel, sep)`），POSIX 与 Windows 两种形状各自按自己的
分隔符拒绝；`inside()` 传宿主分隔符，`isAbsolute` 继续覆盖跨盘符/跨根的情形。

新增回归测试在**任意平台**上同时断言两种形状，包括当初出错的那两个交叉用例
（POSIX 逃逸在 Windows 规则下、Windows 逃逸在 POSIX 规则下），因此「本机是 Windows 所以
本地跑绿」再也掩盖不了这个问题。

这条缺陷值得单独记录：它说明**测试没有在目标平台执行过，就不算通过**。在本轮之前，
这个测试文件不在任何测试脚本里，从未在 CI 上跑过。

### 3.5 新旧 QA 构建共享命名空间（重要限制）

改名只隔离了**显示名与安装目录**。以下三项在新旧 QA 构建之间是**共享**的，因为 identifier
被有意保持不变：

| 命名空间          | 新 QA `Shishi QA V1.1-RC1`             | 旧 QA `Shishi QA RC2D`          | 是否共享 |
| ----------------- | -------------------------------------- | ------------------------------- | -------- |
| Tauri identifier  | `app.shishi.todo.qa`                   | `app.shishi.todo.qa`            | **共享** |
| 数据根            | `%APPDATA%\app.shishi.todo.qa`         | 同左                            | **共享** |
| 凭据服务          | `app.shishi.todo.rc2d-qa.secure-token` | 同左                            | **共享** |
| Windows AUMID     | `app.shishi.todo.qa`                   | 同左                            | **共享** |
| 安装目录          | `%LOCALAPPDATA%\Shishi QA V1.1-RC1`    | `%LOCALAPPDATA%\Shishi QA RC2D` | 分离     |
| 卸载项 / 快捷方式 | `Shishi QA V1.1-RC1*`                  | `Shishi QA RC2D*`               | 分离     |

两个后果必须在验收时如实记录，不能含糊：

1. **在已用过旧 QA 的用户环境里，不能假定 QA 与旧 QA 数据完全隔离。** 新构建启动时会打开
   同一个 QA 数据根与同一批 QA 凭据，可能对旧 QA 的 SQLite 执行迁移。这在 QA 通道内部是
   预期行为（同一个通道 = 同一份数据），但它**不是**一次干净的隔离实验。
2. Windows 通知注册也按 AUMID 归属，因此新旧 QA 共用同一条通知注册项。要证明"通知只属于
   本次构建"，必须用**从未安装过任何 QA 构建**的干净环境，或者先记录旧 QA 数据根与通知
   注册的基线快照，再对比增量。

因此 §4 的 Runbook 要求一次性 VM 且 `%APPDATA%\app.shishi.todo.qa` 不存在。在既有 QA
机器上执行只能算"回归验证"，不能算"隔离验收"。

## 4. 隔离 VM 验收 Runbook（可直接执行）

前提：一次性 Windows VM（Windows 11 或 Server 2022+，桌面体验完整），
**不加入任何已有 Dev/Stable 数据**，登录账号为专用 QA 用户。

```powershell
# 0. 基线与产物（在能访问 GitHub 的机器上）
#    artifact: shishi-qa-v1.1-rc1-windows  ← 名字里带候选版本
#    installer / exe 的 SHA256 必须来自合并后 main 的那次 dispatch（§10），
#    不能沿用 §5.1 中 a4fa7c97 的历史值

# 1. VM 内先证明隔离前提：三个数据根都不存在
Test-Path "$env:APPDATA\app.shishi.todo"       # 必须 False（Stable）
Test-Path "$env:APPDATA\app.shishi.todo.dev"   # 必须 False（Dev）
Test-Path "$env:APPDATA\app.shishi.todo.qa"    # 必须 False（QA，见 §3.5）
Get-ChildItem "$env:LOCALAPPDATA" -Filter "Shishi*"   # 必须为空

# 2. 安装 QA 包（静默）
Start-Process .\Shishi-QA-V1.1-RC1_1.1.0-rc1_x64-setup.exe -ArgumentList "/S" -Wait

# 3. 证明安装身份
(Get-Item "$env:LOCALAPPDATA\Shishi QA V1.1-RC1\todo-native.exe").VersionInfo |
  Format-List ProductName,ProductVersion      # Shishi QA V1.1-RC1 / 1.1.0-rc1

# 4. 证明隔离：Dev/Stable 数据根仍不存在，QA 数据根新建且只属于 QA
Test-Path "$env:APPDATA\app.shishi.todo"       # 仍必须 False
Test-Path "$env:APPDATA\app.shishi.todo.dev"   # 仍必须 False
Test-Path "$env:APPDATA\app.shishi.todo.qa"    # 首次启动后为 True

# 5. ExpectedCommit 三态（用 CI 产出的 SHA 与 commit）
.\scripts\qa\native\run-windows.ps1 -AppExe "$env:LOCALAPPDATA\Shishi QA V1.1-RC1\todo-native.exe" `
  -ExpectedCommit <main-sha> -DiscoverOnly          # MATCH
.\scripts\qa\native\run-windows.ps1 -AppExe ... -ExpectedCommit 0000000000000000000000000000000000000000 -DiscoverOnly
                                                     # MISMATCH → 非零退出
.\scripts\qa\native\run-windows.ps1 ... -AllowCommitMismatch -DiscoverOnly
                                                     # MISMATCH_ALLOWED → 0，且记录为「刻意」

# 6. IPC 溯源：应用内 qa_build_identity 必须返回
#    identifier=app.shishi.todo.qa、commit=<main-sha>
#    且与 manifest.json 的 appExeSha256 一致

# 7. 通知：真实到期后观察通知中心条目、横幅是否出现、点击是否激活
#    只记录实际观察到的结果；注册表 PeriodicNotificationCount 不作为横幅/点击证据

# 8. 卸载并证明数据保留在别处
Start-Process "$env:LOCALAPPDATA\Shishi QA V1.1-RC1\uninstall.exe" -ArgumentList "/S" -Wait
Test-Path "$env:LOCALAPPDATA\Shishi QA V1.1-RC1"   # 必须 False
Test-Path "$env:APPDATA\app.shishi.todo"           # 仍必须 False（Dev/Stable 从未被碰过）
```

Runbook 的每一步都对应 §5 的一个状态项；没有真机就不能把任何一项写成 PASS。
