## C. Release Config Merge Semantics

**问题**：`resolveAppConfig` 用顶层展开，而 Tauri 用嵌套 JSON Merge Patch。

**最小复现（修复前 exit 1，8 个叶子丢失）**：`bundle.targets`、`bundle.category`、
`shortDescription`、`longDescription`、`bundle.macOS.minimumSystemVersion`、
以及 **`app.security.csp` 与 `app.security.capabilities`**。

**额外发现（超出任务书）**：同一展开还丢掉 `app.security`（CSP + capabilities），因为 dev 配置声明了 `app.windows`。
这是**安全相关的建模偏差**，不是纯元数据问题。

**修复**：新增 `applyMergePatch`（对象递归、`null` 删除、数组/标量替换，**无按字段特例**）与
`mergeTauriConfig(...configs)`（base 优先、左到右折叠）；`resolveAppConfig` 折叠 base + dev + 可选额外配置，六个既有字段语义不变。

**契约测试**：两个测试读取磁盘上**三个真实配置文件**，用测试内**独立实现**的参考算法对比，断言 dev 合并后必须存活的
嵌套键（targets / category / descriptions / icon / `macOS.minimumSystemVersion` / `bundle.windows.nsis.installMode` /
`app.security` / `app.windows` 标题 / `build.beforeBuildCommand`），并带**敏感性守卫**（断言旧展开确实缺这些键）。
矩阵：无覆盖、productName/identifier/version/nsis 覆盖、保留 publisher、保留 macOS、嵌套深合并、`null` 删除、多配置顺序、
错误版本拒绝、身份冲突拒绝。测试数 60 → **75**。

## D. QA Harness Reliability

**实测问题**：修复前 `-DiscoverOnly` 盲目优先 `target/release/todo-native.exe`；该文件现在是 **Dev** 构建，
命令直接失败（`refusing non-QA app ProductName=Shishi Dev`）。更早时它可能静默选中旧二进制。

**修复**：策略抽为纯模块 `scripts/qa/native/harness-target.mjs`，PS 脚本只探测与执行。

| 路径                      | 规则                                                                                                                                  |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 显式 `-AppExe`            | 必须存在、ProductName 为 QA、可选 `-ExpectedSha256` / `-ExpectedVersion`                                                              |
| `-Install` + `-Installer` | 必须**恰好一个** QA 包；安装后解析**已安装** exe，绝不回退 release 构建                                                               |
| 均未提供                  | 忽略非 QA 候选（并列出），取**最新 QA 构建**；mtime 混淆窗口内两个不同 sha ⇒ `AMBIGUOUS_TARGET`                                       |
| 新鲜度                    | 选中项旧于更新的可用 QA 构建且 sha 不同 ⇒ `STALE_TARGET`（打印候选路径/时间/版本/sha 与应传旗标）；`-AllowStaleTarget` 为唯一显式覆盖 |

provenance 写入 `environment.json` / `provenance.json` / `manifest.json` / `harness-target.decision.json`：
git commit、选择模式、二进制路径/版本/sha256、安装包 sha256。

## E. Android CI Smoke

**本轮最重要的工程结论：Android 构建第一次真正跑通。**

**第一次 CI（run 41172510099，43s 失败）提供了定位信息**：首个失败步骤是 SDK provision，
报 `Failed to find package 'platforms;android-37'` —— CLI 2.12.4 模板 `compileSdk = 37`，而 android-37 尚未进入稳定通道。

**修复（`058420c`）**：稳定通道 → `--channel=3` preview → 都不可用则 `::warning::` 并移交 build 判定；
仍保留「一个平台都没有 ⇒ 失败」的硬门禁；**provision 告警永不等于通过**。

**第二次 CI（run 41172756868）**：**success**（5m45s），job `Stage 1 - aarch64 debug APK (dev identity)`，
产物 `android-smoke-apk-arm64` = **41,487,881 B**。
校验：Gradle `applicationId`/`namespace` == `app.shishi.todo.dev`、无 `applicationIdSuffix`、
`tauri.properties` 的 `versionName` == `0.0.1-dev.1`、`versionCode` 为正整数；
`aapt2 dump badging` 复验 package / versionName / `arm64-v8a`。

**CLI 事实来自 2.12.4 源码**（非试错）：`android init` 接受 `-c/--config`；`--target` 取
`aarch64|armv7|i686|x86_64` 且**省略会构建全部四 ABI**；`--apk` 与 `--aab` 可同时；`tauri.properties` 由 **build** 写入而非 init。

唯一故意偏离：额外安装 `platforms;android-37`（见上），其余 setup 包列表与任务书逐字一致。

步骤：

```bash
git fetch --all --tags --prune

git status --short                       # 必须为空

# 单入口：只推 tag，不要再叠加 workflow_dispatch

gh release download 0.0.1-dev.1 --pattern 'SHA256SUMS.txt' --dir /tmp/rel
cat /tmp/rel/SHA256SUMS.txt
gh release view 0.0.1-dev.1 --json isDraft,isPrerelease,assets   # 转正后复核
gh release download 0.0.1-dev.1 --pattern 'release-manifest.json' --dir /tmp/rel
# 断言 manifest.commit.tagSHA == buildSHA == <CANDIDATE_SHA>
```

失败恢复：校验失败 ⇒ 保留 draft 不转正（设计如此）；人工检查后可 `gh release delete 0.0.1-dev.1 --yes --cleanup-tag=false`（**只删 draft，不删 tag**）。
