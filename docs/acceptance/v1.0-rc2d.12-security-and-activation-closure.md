## C. QA Evidence Path Security

**模型**：配置路径被拆成「授权根 + 一个惰性文件名」。

```text
configured path -> split_evidence_path -> validate_evidence_file_name (pure)
  -> create_dir_all(root) -> verify_created_directories (reparse 检查)
  -> canonicalize(root) 一次 -> authorize_evidence_root (canonical 之后判定)
  -> OpenOptions(append|create) + FILE_FLAG_OPEN_REPARSE_POINT
  -> verify_opened_evidence(handle: 属性/普通文件/canonical 目标仍在根内)
```

**为什么不是简单 `canonicalize()`**：文件可能尚不存在（无法 canonicalize），目录重解析与检查后替换需要分别处理，因此改为
「单组件文件名 + 预创建根 + 句柄级验证」：可写文件名不含分隔符，穿越在**结构上不可能**；最终组件在**已打开句柄**上验证，
不存在检查后再替换的窗口。

**授权策略**（`authorize_evidence_root`）：先拒绝 canonical 根落在 Stable / Dev 数据根内（用组件比较，
Windows 大小写不敏感，`app.shishi.todo.qa` 不会被误判为在 `app.shishi.todo` 内）；再允许
canonical QA 应用数据根内；仅当配置为**相对路径**时允许工作目录树内。其余一律 fail closed。

**测试结果（21 项）**：

## D. Release Transaction Safety

**修复前**：发布 job 先删旧资产（写），再做只读门禁；既可能破坏已发布 Release，也没有「同版本已存在」的判断。

**修复后的阶段**：

```text
resolve tag -> verify commit SHA -> build all platforms -> verify artifact set
  -> verify identity/version -> verify checksums -> manifest
  -> [read-only] check existing release + provenance guard
  -> create DRAFT -> verify remote asset set -> flip public (single PATCH)
  -> verify published provenance
```

| 要求                   | 实现                                                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 移除发布前自动删除     | 已删除该步骤；仅注释中说明为**人工**维护流程，可执行行内不存在 `gh release delete` / `delete-asset`                      |
| 已存在 Release 策略    | 缺席→create-draft；draft 与本次完全一致→publish-draft；公开且一致→noop（零写操作）；任何差异→拒绝并逐项点名              |
| 不覆盖已有公开资产     | 同版本默认不可变；身份/版本/文件名/hash 任一不同即拒绝                                                                   |
| 同 Tag 不同身份        | 拒绝（历史 `0.0.1-dev.0` 为 stable 身份，重跑必被拒）                                                                    |
| 发布后校验远端资产     | draft 的远端资产按 name+size+hash 与本地 manifest 比对                                                                   |
| Tag SHA 与 Manifest    | release target commit 必须等于 TagCommitSHA，且远端 manifest 资产记录同一 SHA                                            |
| 不同分支 dispatch      | manifest 记录 `github.workflow_sha`；与 TagCommitSHA 不同则拒绝，除非显式 `allow_foreign_workflow`                       |
| 并发 / 重跑 / 部分失败 | `cancel-in-progress: false`（workflow 与 publish job 双级），按版本串行；部分失败留下**不可见 draft** 而非不完整公开发布 |

**验证**：`pnpm run test:release` **60/60**（33 原有 + 27 新增，覆盖 14 项矩阵与 8 项静态断言：无 delete、
门禁前无写操作、draft 转正顺序、全部 Action 仍 pin 40 位 SHA、发布不可取消）。
**NOT_RUN**：未执行真实 GitHub Actions 发布，未对真实 Release 调用 `gh api`（本轮禁止）；决策层为纯函数 + fixture 验证。

## E. DetailPanel Render Confirmation

**修复前**：确认由 App 自己的 signal 推导，证明不了组件挂载、证明了不渲染的是目标任务、更证明不了可见。

**修复后**：`DetailPanel` 成为确认方。

```text
Notification Activation -> Native Validation -> Task Load
  -> Navigation Transaction -> Selection Commit
  -> DetailPanel onMount / deferred effect（报告 props.task.id + generation）
  -> 导航器比对 taskId 与 generation -> ACK opened
```

| 要求                       | 实现                                                                                                  |
| -------------------------- | ----------------------------------------------------------------------------------------------------- |
| 信号来自组件生命周期       | `onMount` + `createEffect(on(() => [props.task.id, props.navigationGeneration], …, { defer: true }))` |
| App 不能自行确认           | 派生 effect 已删除；`setRenderedDetail` 仅作为 `onRenderedDetail` 回调出现一次                        |
| taskId + generation 匹配   | 面板报告自己的 `props.task.id`，App 侧选择无法代替                                                    |
| 详情关闭不能 ACK           | `onCleanup` 报告 null                                                                                 |
| 账号切换后旧组件不能 ACK   | 导航器在确认回调内重比 `activeAccountId()`                                                            |
| 被手动导航取代立即失效     | 视图报告其它 taskId 即视为被取代                                                                      |
| 卸载后信号不能再次触发     | `detached` 守卫丢弃卸载后的任何非 null 报告                                                           |
| 超时/Abort 后无迟到 opened | 事务已 settle，迟到报告被忽略                                                                         |
| 回滚不覆盖更新的选择       | 仅当本事务仍拥有视图时回滚                                                                            |
| 无 selector / sleep        | App.tsx 无 `querySelector`；确认路径无新增 timer                                                      |

**可见性边界**（明确定义，不使用 mounted 代替可见性）：确认语义为「组件已把目标任务提交进渲染输出」；
被 modal / backdrop / 移动端布局遮挡**不在 ACK 判定范围内**，由 Playwright 断言真实 DOM 渲染与卸载。

**测试**：DetailPanel 真实 Solid 渲染 6 项；导航器新增 4 项（错误 task、过期 generation、关闭中途、账号切换）；
mini App 树集成 3 项；Playwright 2 项。前端总计 **115**（原 102），bridge 30 项未改。

## F. Activation TTL Boundary

**修复前**：`take_for_listener_at` 只取一次 `now`，reserve 与 commit 共用。验证（账号注册表 + SQLite）跨过 TTL 时，
commit 仍用验证前的时间戳，**已过期的激活被交付**。

**修复后**：每个状态边界各自采样时钟（reserve / commit / restore / 验证失败 / reload 重排 / acknowledge）；
生产路径为 `Instant::now()`，测试通过私有 `Clock` 边界显式 pin 并推进读数。commit 按**提交时刻**判过期，
并给出可诊断的新码 `ACTIVATION_EXPIRED_DURING_VALIDATION`。

| 边界用例                                                      | 结果                                                 |
| ------------------------------------------------------------- | ---------------------------------------------------- |
| 299.999s（配额内）                                            | 交付                                                 |
| 恰好 300s                                                     | 过期（与 `is_expired` 的 `>=` 语义一致，已断言定义） |
| 300.001s                                                      | 过期                                                 |
| T0 准入 / T0+290s reserve / T0+301s 验证结束                  | **commit 拒绝**，交付 0 条，诊断 1 条                |
| 299s 慢验证                                                   | 正常交付                                             |
| reload 后过期 / 慢验证中 session 变化 / 旧 ACK / 失败后新激活 | 分别过期 / 归还而非丢弃 / 拒绝 / 正常交付            |

D11 的 `ACTIVATION_TTL = 300s`、`MAX_REQUEUES_PER_ACTIVATION = 1`、单锁、reservation 所有权事务、容量 8 **均未改动**；
测试不再依赖机器 uptime（无 `checked_sub`、无 `Instant - Duration`）。

## G. Runtime Activation Diagnostics

`ActivationDiagnostic`（最小必要字段）：`activation_id`、`notification_instance_id`、`event_type`、
`rejection_code`、`terminal_outcome`、`delivery_attempt`、`session_correlation`（会话 id 的 16 位十六进制
FNV-1a 指纹，原始会话字符串不出模块）、`timestamp_millis`（相对窗口起点的单调毫秒）。

| 要求                | 实现                                                                                                      |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| 有界内存            | 容量 64 环形缓冲，读写时按 300s TTL 剪枝，不落盘                                                          |
| 不扩大 WebView 权限 | 无新增命令；沿用既有只读 `native_recovery_diagnostics` / `native_export_recovery_diagnostics` 的 bundle   |
| 不泄露敏感信息      | 不记录 task id/title、账号 id/email、token、路径、原始通知文本；红化测试断言这些字符串不出现              |
| 不影响业务状态机    | 记录为 best-effort，失败不改交付结果（有专门测试）                                                        |
| 可关联              | duplicate ACK（非终态记录）、overflow、expiry、`ACTIVATION_EXPIRED_DURING_VALIDATION`、跨账号拒绝均可关联 |
| 单一终态            | duplicate_ack 设计为非终态，测试证明一个激活不会同时拥有两个矛盾终态                                      |

测试：FIFO、容量淘汰（第 65 条淘汰第 1 条）、TTL 剪枝（299.999s 保留 / 300s 剪除）、红化、重复 ACK 关联、
跨账号拒绝关联、overflow 关联、导出到 diagnostics bundle、并发（4 线程 × 40 保持有界）、记录失败不影响交付、单一终态。
