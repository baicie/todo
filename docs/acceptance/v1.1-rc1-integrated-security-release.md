## 3. 未授权发布的复现与修复（P0）

### 3.1 复现（修复前状态）

原实现：`release-dev.yml` 由 tag push 触发，并在同一个 run 里把 draft 翻成 public，
唯一的闸门是 `environment: dev-pre-release`——一个 workflow 既读不到、也无法证明的仓库设置。

本仓库当时的真实状态（本轮实测）：

```text
gh api repos/baicie/todo/environments/dev-pre-release        → HTTP 404 Not Found
gh api repos/baicie/todo/branches/main/protection            → HTTP 404 Branch not protected
git ls-remote --tags origin | grep 0.0.1-dev                 → 只有 0.0.1-dev.0
gh release list                                              → 只有 Shishi 0.0.1-dev.0 (Pre-release)
```

即：Environment 根本不存在 ⇒ 没有任何人工审批 ⇒ 推一个 tag 就足以公开 Release。

### 3.2 修复设计

采用方案 **B（独立 Publish Workflow）+ Environment 作为第二层**，并保留 fail-closed 的
Environment 探针：

1. `release-dev.yml` **只能 stage draft**：tag push → 构建 → 写 manifest / SHA256SUMS →
   `verify-assets` → `check-existing` → 单次写入创建 draft → `verify-draft` → evidence。
   该文件全文不含 `publish-draft`（有测试断言）。
2. `publish-dev.yml` **只有 `workflow_dispatch`** 触发，三道相互独立的闸门：
   - 手动 dispatch（无 push / tag / schedule 触发器）；
   - 必须键入精确确认短语 `publish <tag>`；
   - `dev-pre-release` Environment 的 `required_reviewers` 规则，且 GitHub 在审批前不启动
     `publish` job。
3. **Environment 探针 fail-closed**：`environment-gate` 在审批前的只读 job 里运行，
   把结果作为 `EnvironmentGate` 传给 `authorize-publish`。403 / 404 / 任何读不到都记为
   `unverified`，**绝不解释为"已配置/已批准"**。
4. 审批通过后、写入前，publish job 重新证明世界没有移动：checkout 到 tag commit、
   `guard-workflow`、`adopt-draft`（下载 draft 的 manifest 与 SHA256SUMS 并校验字节）、
   `verify-draft --from-manifest --expect-draft-sha`、再次 `authorize-publish`，最后**唯一一次**
   `PATCH draft=false&prerelease=true`。
5. `--expect-draft-sha` 把 manifest 的**字节**钉在 staging run 记录的那个 sha256 上，
   使"用 draft 的 manifest 复核 draft"不构成循环论证。

## 4. Web 共享数据账号隔离

### 4.1 威胁模型

同一台设备上 A 登出、B 登录。若本地共享数据与 outbox 不区分账号，则：

- B 会看到 A 的共享清单与任务内容；
- A 未发送的离线编辑会被 **B 的凭据** 重放，写进错误身份；
- "清空所有缓存"不是解法——它会把 A 尚未发送的离线编辑一起销毁。

### 4.2 实现

| 层           | 机制                                                                                                                                                                    |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 本地空间绑定 | `sharedMeta.accountBinding` 存 `{email, apiUrl}`（归一化小写 / 去尾斜杠）。`claimBinding` 在**一个事务内**声明或确认；不匹配则拒绝，**不覆盖、不清空**。                |
| 空空间归属   | 无列表的空间由当前登录账号认领；有数据但无绑定的历史空间，只有个人空间 `boundAccount` 邮箱一致时才收养。                                                                |
| 会话栅栏     | `SharedSession {token, account}` + `runToken` / `runOwner` / `bindingDirty`；`fence(generation)` 使旧会话的在途回调失效；`assertSameSession()` 在每次读写与推送前校验。 |
| 推送绑定     | 推送前重读列表，`access !== 'active'` 或无 snapshot 即 `stop`；每个请求带当前 token，不使用"最后一次见到的 token"。                                                     |
| Native       | `MemorySharedStore`（进程内），不写入 webview IndexedDB，跨原生账号无残留。                                                                                             |

断言（`apps/app/src/sync/shared-account-isolation.test.ts`）：

```text
ACCOUNT_A_CACHE  != ACCOUNT_B_CACHE     （sharedLists / sharedTasks 内容互不可见）
ACCOUNT_A_OUTBOX != ACCOUNT_B_OUTBOX    （A 的 pending op 不会以 B 身份发出）
```

### 4.3 C1 十步双账号场景（已实现为测试）

1. A 登录，创建共享清单并在离线状态编辑；2. 断网，编辑进入 outbox；
2. A 登出，个人数据保留；4. B 登录；5. B 在发出任何 API 请求**之前**打开共享列表页
   （此时不得看到 A 的任何数据）；6. B 联网并触发同步；7. 断言 B 的缓存与 outbox 均不含 A 的
   内容，且没有任何以 B 身份发出的 A 的 op；8. A 重新登录，其 pending op 仍在；
3. 重连后 A 的 op 以自己的凭据重放；10. A、B 同时是同一共享清单成员时，各自看到一致的服务端状态。

### 4.4 C3 竞态矩阵

| 竞态                     | 处理                                                | 测试 |
| ------------------------ | --------------------------------------------------- | ---- |
| 登出 vs 在途 HTTP 响应   | 响应落地前 `assertSameSession`，不匹配即丢弃        | ✅   |

| 过期响应                 | 见上                                                | ✅   |
| 离线切换账号             | 绑定校验在读路径上，离线也不会串号                  | ✅   |

## 5. Outbox Session Fence

`SharedSyncEngine` 的不变量与对应测试：

| 不变量                          | 测试                                                              |
| ------------------------------- | ----------------------------------------------------------------- |
| 不重复建任务                    | lost ACK for create / replayed receipt with non-adjacent revision |
| 超时不等于永久丢失              | lost ACK for patch 结算为 applied，不退化为 rejected              |
| 409 → 新 Snapshot + 正确 Rebase | pull-and-rebase；同字段冲突不覆盖                                 |
| 不静默丢弃有价值的离线编辑      | 撤销 / 删除后标记 `rejected` 并保留，绝不 `delete`                |
| 被拒绝的 op 不无限自动重试      | 拒绝即停；只有显式重试才再发                                      |
| 列表删除 / 账号移除后停止推送   | `access !== 'active'` → `stop`                                    |
| viewer 提升 / 降级              | 提升后可写、降级后拒绝并拉新角色                                  |
| 冲突不得当作成功                | 409 不入 receipt，不改本地 revision 为服务端值以外的东西          |

## 6. PostgreSQL API 输入边界

### 6.1 先复现，不靠注释推断

在隔离 PostgreSQL 18.6 上运行被 `#[ignore]` 的原始用例，实测 HTTP 状态确为
`500 INTERNAL_ERROR`（NUL 写入 `TEXT` 失败、超范围 `date` 失败），而非假设。

### 6.2 修复

- 统一校验助手：`reject_unstorable_chars` / `validate_text` / `validate_note` /
  `validate_optional_text` / `validate_due_on`。
- 非法客户端输入 → `400 {code: "VALIDATION_FAILED", message}`；**不写库、不推进 revision、
  不写 op receipt、不透出 SQL 内部信息**。
- 不吞掉数据库异常：只有"值本身不可存储"走校验，真实 DB 故障仍上抛。
- 合法 Unicode 语义不变；合法日期范围**不缩窄**。

### 6.3 `due_on` 下界（本轮修正）

原实现只按年份判断 `-4713..=5874897`，因此放行了 `-4713-11-23`——PostgreSQL 拒绝的日期，
于是客户端输入错误再次变成 500。实测边界：

```text
select '4714-11-24 BC'::date  → 4714-11-24 BC     （儒略日 0，首个可存储日）
select '4714-11-23 BC'::date  → ERROR: date out of range
select '5874897-12-31'::date  → 5874897-12-31     （最大）
select '5874898-01-01'::date  → ERROR: date out of range
```

修正为精确下界 `PG_DATE_FLOOR = -4713-11-24`（天文纪年）。上界无需额外守卫：
`chrono::NaiveDate` 最大到 `262143-12-31`，远低于 PostgreSQL 上限，超出的年份在 JSON 反序列化
阶段就已被 400 拦下。

测试：单元 `due_on_uses_postgresqls_exact_lower_bound`；真实 PG
`shared_routes_reject_values_postgres_cannot_store` 增加 `-4713-11-23` 拒绝分支，并断言
`-4713-11-24` 本身仍被接受且原样回读（防止"修复"变成缩窄合法范围）。

### 6.4 已关闭的缺陷清单

`known_defect_shared_routes_reject_values_postgres_cannot_store` 已重命名为
`shared_routes_reject_values_postgres_cannot_store`，**移除 `#[ignore]`**，CI 不再使用
`--skip known_defect_`。当前边界套件 12 项在真实 PostgreSQL 18.6 上全绿。

## 7. 双账号与共享权限矩阵

服务端为权威，前端 `editable` 不参与任何判定。矩阵在
`apps/api/tests/postgres_shared.rs` 与 `apps/api/tests/postgres_boundaries.rs` 中逐格断言：

| 角色 \ 操作    | 读列表                              | 建/改/删任务 | 邀请 | 移除成员 | 改角色 | 删除列表 |
| -------------- | ----------------------------------- | ------------ | ---- | -------- | ------ | -------- |
| Owner          | ✅                                  | ✅           | ✅   | ✅       | ✅     | ✅       |
| Editor         | ✅                                  | ✅           | ❌   | ❌       | ❌     | ❌       |
| Viewer         | ✅                                  | ❌ 403       | ❌   | ❌       | ❌     | ❌       |
| Non-member     | ❌ 404                              | ❌ 404       | ❌   | ❌       | ❌     | ❌       |
| Removed member | ❌ 403 `SHARED_LIST_ACCESS_REVOKED` | 同左         | —    | —        | —      | —        |

邀请语义（`shared_list_invitations...`）：

- 未注册邮箱可被邀请，注册后可见并接受；
- 重复接受、已接受后再接受 → 幂等或 `409 SHARED_INVITATION_NOT_PENDING`；
- 拒绝后不可再接受；不存在 / 他人邀请 → `404 SHARED_INVITATION_NOT_FOUND`；
- 同一邮箱重复邀请 → 复用同一行、可改角色（部分唯一索引保证只有一条 pending）；
- 移除成员 → 旧 token 立刻 `403 SHARED_LIST_ACCESS_REVOKED`，旧邀请不能重放；
- 重新邀请恢复访问，角色以新邀请为准；
- 列表删除后邀请消失且不可接受；
- A 的邀请 id 被 B 使用 → `404`（不泄露存在性）。

**已知设计缺口（明确记录，非本轮回归）**：v1 不提供 owner 侧"撤销/取消邀请"接口。
迁移中 `status = 'revoked'` 已保留，但 API 未暴露。这是有意的设计闸门，不是遗漏。

## 8. 真实 API + 真实 PostgreSQL 联合测试

`scripts/shared-e2e.mjs` 在 CI（`.github/workflows/api.yml` 的 `Shared-list multi-session E2E`
step）中对 `cargo run -p todo-api` + PostgreSQL 运行，**不是 mock**。CI 实测输出
（Run `41478546656`）：

```json
{
  "conflictRejected": true,
  "lostAckReplayedOnce": true,
  "opIdConflict": true,
  "concurrentWrite": "one-200-one-409",
  "crossAccountInvitation": "hidden-and-refused",
  "viewerWrite": "forbidden",
  "roleChange": "promote-allow-demote-deny",
  "rejectedOpRetry": "executes-once-after-promotion",
  "deletedList": "owner-and-member-see-404",
```

本轮新增的三组断言：

- **角色升降级**：viewer→editor→viewer，同一写入依次被拒 / 允许 / 拒；每次改角色前重新读
  revision，测的是服务端强制而非陈旧快照。
- **被拒绝 op 的重试**：因权限被拒的 op **不写 receipt**，提升后用同一 `op_id` 重试会真正执行
  且只创建一个任务。客户端 outbox 的安全重试依赖这一点。
- **列表删除**：owner 与 member 的读与推送都得到 `404 SHARED_LIST_NOT_FOUND`（而非 403），
  这是客户端应丢弃本地影子而不是报权限问题的信号。

**GUI E2E 未运行**：`tests/e2e/tests/shared.spec.ts` 仍以 mock 为主，本轮没有可安全隔离的
浏览器设备用于真实 GUI 双端验证，因此 `SHARED_SYNC_REAL_API_E2E_READY` 只按 API 层判定为
PASS，GUI 层记为 NOT_RUN。

| #   | 严重度 | 发现                                                    | 状态             |

| S4  | P1     | 共享路由对 NUL / 超范围日期返回 500 泄漏内部错误        | 已修复 `57273a1` |
| S5  | P1     | `due_on` 年份检查放行 `-4713-11-23`，仍可 500           | 已修复 `e1dc30a` |
| S6  | P1     | macOS `toolchain-<arch>.json` 让 draft 无法发布         | 已修复 `2ba86a3` |

独立审查过的攻击面与结论：

- **跨账号读写**：所有共享路由以 `AuthUser`（token 唯一身份）为准，`lock_access` 用
  `FOR UPDATE OF l, m` 锁定列表与成员行；无 `user_id` 入参可被客户端伪造。
- **旧 token / 旧 session**：登出后 access token 立即 401；session 校验含
  `revoked_at` / `expires_at` / 用户删除 / 设备吊销四项。
- **API 权限绕过**：非成员得到 404（不泄露存在性），被移除成员得到 403（客户端需要这个
  区分来转为只读）。邀请 id 被他人使用 → 404。
- **Outbox 错误重放**：`OP_ID_CONFLICT` 阻止跨 actor 复用 op_id；被拒绝的 op 不写 receipt。
- **SQL 事务一致性**：revision 递增、任务写入与 receipt 在同一事务；冲突回滚不推进 revision。
- **版本 / 构建来源**：manifest 记录 tag SHA、build SHA、workflow SHA、run id；publish 前
  重新校验 tag ref 指向。
- **未授权发布**：见 §3。
- **恢复不完整**：见 §9，指纹覆盖所有 public 表。
- **CI 产物中的敏感信息**：evidence 与日志不含 token / 凭据；manifest 只含版本、SHA 与
  工具链版本。
