## 4. 关键操作步骤与证据链

### 4.1 真实账号/登录

1. 通过真实安装包启动应用；WebView2 CDP 显示页面 `http://tauri.localhost/`。
2. 使用 Native 命令创建 A/B 两个云账号（不同邮箱、同一测试 API）。
3. 在真实设置/同步界面填写 API/email，点击发送验证码；使用开发 API 的 `AUTH_DEV_CODE=246810`。
4. 选择“合并本机与云端”；应用真实调用 `syncInitializeCloud`，A/B 各生成云端用户和任务。
5. 服务器侧 PostgreSQL 查询：A live=5，B live=2；本地 A=5，B=2（B 另有 1 软删除行）。

真实 API 健康检查：

```json
{ "checks": { "database": "ok", "mail": "ok", "migrations": "ok" }, "status": "ready" }
```

### 4.2 同步中切换/未上传 outbox

1. 暂停本地 API 进程（NtSuspendProcess），制造同步请求挂起。
2. A 本地创建任务；点击“立即同步”；在请求未返回时通过真实 UI 切换 B。
3. UI 提示“当前账号还有 1 条未同步修改”；切换成功，旧进程退出、新进程打开 B。
4. 恢复 API；A 本地仍有任务且 `outbox=1`，B 不受影响；服务器 A 仍为旧数量。
5. 切回 A，同步将 pending 上传；A `outbox=0`，服务器 A=5。

### 4.3 目标损坏回滚与重试

1. 真实 prepare B，RESTART_REQUIRED 后用独立 watcher 在 2ms 轮询 journal 并强杀进程。
2. 备份 B DB 后，把 B 的 `shishi.sqlite3` 替换为 24 字节非 SQLite 文本，删除 WAL/SHM。
3. 启动应用：journal 变 `FAILED/TARGET_INVALID`，active 恢复 A；A 数据/Token 不变。
4. 从备份恢复 B DB；再次 prepare/request B 成功，B 数据和 Token 恢复。
5. 冷重启应用后 B Token 仍可读，A Token 被跨账号拒绝。

### 4.4 ReplaceFileW fallback journal 恢复

在应用停止时构造受控文件状态：

- `accounts.json` 写入无效内容；
- 一个 `.accounts.json.<uuid>.tmp` 无效 source；
- 一个 `accounts.json.old-<uuid>` 有效 backup（active A）；
- 写 `accounts.json.replace-journal` 指向 source/backup。

启动后应用恢复有效 A registry，删除 replace-journal。实际没有让 `ReplaceFileW` 返回失败，因此该场景分类为 **PARTIAL**。
