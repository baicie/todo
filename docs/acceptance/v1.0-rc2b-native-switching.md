## 1. 实现范围

### 1.1 Rust 账号切换协议

新增 `crates/native-accounts/src/switch.rs`：

- `native_list_accounts`
- `native_create_account`（pending，空独立库）
- `native_prepare_account_switch`
- `native_request_account_switch`
- `native_abort_account_switch`
- `native_account_switch_status`
- `native_mark_account_verified`
- `native_account_context` 增加 `api_url`

Native registry 仍是唯一 active authority。WebView 只提交注册过的 opaque account id；数据库路径、账号目录均由 Rust 派生，不接受路径参数。

### 1.2 冷切换

```text
ACTIVE
  -> PREPARED            目标库完整性/身份预检通过；写 pending-account-switch.json；关闭写门
  -> RESTART_REQUIRED    取消旧账号提醒成功；请求桌面进程重启
  -> VERIFYING_TARGET    新进程验证 target 后原子提交 registry active
  -> ACTIVE              target Store 打开成功；删除 journal
  -> FAILED              target 校验/打开失败；恢复 source active
```

- `PREPARED` 在重启前从未被 request 时，新进程丢弃并保持 source。
- `RESTART_REQUIRED`/`VERIFYING_TARGET` 在 SIGKILL 后继续。
- 目标缺失、损坏、email/API 服务端身份不符或打开失败时，写 `FAILED` 并恢复 source；不创建空目标库。
- `rollback_pending_switch` 先持久化 `FAILED`，再恢复 registry；`recover_pending_switch` 对 `FAILED` 再修复一次 active 指针，覆盖“标记已写、registry 尚未恢复”的进程死亡窗口。
- 重名同账号 prepare/request 幂等，generation 必须匹配。

### 1.3 运行时写门

`RuntimeGate` 关闭后：

- 普通 `todo_storage` 写通过 lease 计数被拒绝；`begin_switch` 最多等待 2 秒让 in-flight 本地写完成。
- 提醒 schedule/cancel/reschedule 使用 lease，不能再向旧账号队列写。
- Token 读写和账号创建/验证被拒绝。
- 唯一例外是 `sync_clear_session`：quiesce 必须清 SQLite sync-session fence。
- 不热替换 `Arc<TodoStore>`；新进程重新打开 target，旧 SQLite 连接随进程退出释放。

### 1.4 Token / 云配置 / 服务端身份

- 安全存储 key：`cloud-refresh:<account-id>`；legacy `cloud-refresh:default` 只由启动迁移直接读取。
- Tauri token 命令只允许 active account 的 key；其他 key 返回 `CROSS_ACCOUNT_TOKEN`。切换不删除旧 token、不 revoke 服务端 session、不清 outbox。
- cloud config 使用 `shishi.cloud.config[.<account-id>]`；启动时先 `native_account_context`，再写 localStorage active，最后动态加载 App/cloud.ts。
- `AccountRecord.api_url` 与数据库 `kv_state.bound_api_url` 参与切换校验。同邮箱不同 API 服务端创建不同 opaque account；target 绑定到错误服务端时 prepare 拒绝。
- 新账号先 `pending=true`、空 SQLite；登录并写入 bound account/API 后才 `mark_account_verified`。不把 anonymous/default 数据复制给 pending 账号。
- WebView 侧 `switchAccount`/`createAndSwitchAccount` 在 Native 运行时拒绝直接改 localStorage。

### 1.5 提醒隔离

- 原生提醒 ID：`account:<account-id>:<task-id>`。
- 桌面内存队列/移动端持久队列都使用 account 前缀；reconcile 取消其他账号和 legacy 无前缀项。
- 切换 request 先取消当前账号通知并核对残留；失败返回 `REMINDER_ERROR`，不重启、不虚报成功。
- 新进程 setup 调 `cleanup_foreign_queue`，只保留 active account 前缀。
- 旧通知没有任务打开路由；当前实现不会把旧 account 的 task id 解释为 B 的任务。

### 1.6 Native UI

Native Tauri 设置页显示：

- registry 账号列表、当前账号、pending 标记、API 服务端；
- 添加 pending 账号；
- 切换确认与旧账号 pending outbox 数量；
- `FAILED` 切换的回滚状态；
- “未同步修改保留、切换不删除旧凭据”说明。

移动端检测到 Android/iOS 时拒绝冷切换并明确提示，不进入写门。启动失败时 App shell 显示 danger toast，设置页显示恢复 banner。

## 2. 数据边界

```text
app_data_dir/
  accounts.json                       # active + 非敏感账号元数据
  pending-account-switch.json         # 冷切换 journal（成功后删除）
  migration-state.json
  accounts/
    default/shishi.sqlite3            # 默认数据空间（可已绑定 RC2-A 云身份）
    <opaque-uuid-v7>/shishi.sqlite3   # 每账号独立 DB
  migration-backups/
```

- 每账号独立 `device_id/client_seq/outbox/server_shadow/sync_cursor/sync_session`。
- 切换只改变 active 指针和打开的 DB；不搬数据、不派生设备身份、不生成 outbox。
- target 必须在 prepare 前存在且通过完整性与身份检查；target 打开失败时 source 保持可用。
- 旧账号 DB、backup、token、config 均保留；不提供破坏性删除。

## 3. 关键实现点

| 点             | 实现                                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------------ |
| 取消旧提醒     | direct adapter + 失败收集 + 队列残留复核                                                               |
| 旧 HTTP 迟到   | cloud quiesce 失效 generation/session fence；前端测试覆盖；实际进程重启也杀死旧 HTTP 宿主              |
| 写门例外       | 仅 `sync_clear_session`，避免 quiesce 被自身 gate 阻塞                                                 |
| Target 回滚    | registry 先恢复 source，target 原样保留；不删除、不建空库                                              |
| FAILED 崩溃窗  | journal Failed 先落盘，恢复时再修 active；有专项测试                                                   |
| COMPLETE 切号  | active≠migration target 时校验 active DB 与历史 target；缺 active DB 不重建；新账号不继承 legacy token |
| 同邮箱多服务端 | `api_url` 规范化为身份字段；DB 绑定 API 作为二次校验                                                   |
| Legacy 诊断    | `legacy_review_report` 只读返回 reason/source/backup/指纹，不写 registry、不提供 force-bind            |
| 移动端         | 明确 `RESTART_UNSUPPORTED`，UI 拒绝；无“假成功”                                                        |

## 7. 剩余风险

1. **移动端冷切换未实现**：Android/iOS 返回 `RESTART_UNSUPPORTED`；UI 拒绝，不会改 active 或误删旧数据。
2. **旧通知点击**：当前没有通知任务打开路由；若后续加入路由，必须校验 account id。Android 开机 `rescheduleAll` 会先重排持久队列，之后启动清理才移除旧账号项，存在很短窗口。
3. **Pending 账号身份错误**：pending 账号登录时使用不同邮箱/API，`mark_account_verified` 会失败并保持 pending；再次切换到它会被身份检查拒绝，数据保留但需要修复工具。这是 fail-closed 的代价。
4. **REQUIRES_REVIEW**：只有只读报告函数；没有独立人工恢复 CLI 或 UI。不得用“强制绑定”绕过服务端身份校验。
5. **真实重启**：`tauri::process::restart` 在单实例插件、安装包更新和移动端的行为未在真机验证。
6. **系统通知清理失败**：启动清理失败仅记录日志；后续 reconcile 会再报告，但启动瞬间可能仍残留旧通知。
7. **默认数据空间云绑定**：RC2-A 旧 default 可能已绑定云账号；允许切回 default 以避免锁死，但其服务端身份不由 registry 的 `api_url` 校验（DB 自身有 bound API）。
