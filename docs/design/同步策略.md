# 同步策略

> 数据如何在本地存储、远程持久化、多设备间同步，以及冲突如何解决。

---

## 1. 存储层级架构

### 1.1 三层存储模型

```
┌─────────────────────────────────────┐
│         应用层 (UI Layer)            │
│   React Components / Taro Pages       │
└──────────────┬──────────────────────┘
               │ 调用
               ▼
┌─────────────────────────────────────┐
│        Storage 接口层                 │
│   IStorage / ITaskStorage / IListStorage │
│   @repo/todo-model                   │
└──────────┬──────────────────┬───────┘
           │                  │
           ▼                  ▼
┌──────────────────┐  ┌──────────────────┐
│   本地存储层       │  │   远程存储层       │
│  LocalStorage     │  │  RemoteStorage   │
│  (IndexedDB)     │  │  (REST API)      │
└──────────────────┘  └──────────────────┘
```

### 1.2 本地存储选型

| 方案 | 容量 | 优势 | 劣势 | 适用场景 |
|------|------|------|------|---------|
| localStorage | 5MB | API 简单，同步 API | 容量小，字符串存储 | 小型配置项、Token |
| IndexedDB | 无限制（浏览器） | 大容量、支持索引、事务 | API 复杂，异步 | 任务数据、附件 |
| OPFS（文件系统） | 无限制 | 大文件、Streaming | 兼容性一般 | 文件附件（>5MB）|

**当前问题**：`todo-model` 的 `LocalStorage` 实现使用的是 localStorage，会在任务数量增长后溢出。

**改进方案**：迁移到 IndexedDB。推荐使用 **Dexie.js** 封装 IndexedDB：

```typescript
import Dexie from 'dexie';

class TodoDatabase extends Dexie {
  tasks!: Dexie.Table<Task, string>;
  lists!: Dexie.Table<List, string>;
  syncQueue!: Dexie.Table<SyncOperation, number>;

  constructor() {
    super('UniTodoDB');
    this.version(1).stores({
      tasks: 'id, listId, isCompleted, isImportant, addToMyDay, dueDate, createdAt, updatedAt',
      lists: 'id, isSmart, userId, createdAt',
      syncQueue: '++id, entityType, entityId, operation, createdAt',
    });
  }
}
```

## 2. 同步模式

### 2.1 离线优先（Offline-First）

本地数据作为权威数据源，网络仅作为可选的持久化通道。优先保证离线可用。

```
┌──────────────────────────────────────────────────────────────┐
│                      用户操作                                 │
│   创建任务 / 修改任务 / 删除任务 / 切换清单                    │
└────────────────────────┬───────────────────────────────────┘
                         │ 立即写入本地 IndexedDB
                         ▼
              ┌────────────────────────┐
              │   本地 IndexedDB        │  ← 权威数据源
              │   [操作写入 syncQueue]  │
              └────────────┬───────────┘
                           │ 网络可用时
                           ▼
              ┌────────────────────────┐
              │    同步队列             │
              │   SyncQueue (IndexedDB)│
              └────────────┬───────────┘
                           │ 后台异步
                           ▼
              ┌────────────────────────┐
              │    远程 REST API       │
              │   (POST/PUT/DELETE)    │
              └────────────────────────┘
```

### 2.2 存储模式配置

```typescript
interface StorageConfig {
  mode: 'local' | 'remote';
  apiBaseUrl?: string;
  syncInterval?: number;       // 远程轮询间隔（ms），默认 30000
  syncOnReconnect?: boolean;   // 网络重连后自动同步，默认 true
  conflictStrategy?: 'local-wins' | 'remote-wins' | 'manual'; // 冲突策略
}
```

### 2.3 同步触发时机

| 触发条件 | 行为 |
|---------|------|
| 用户操作 | 立即写入本地，同时将操作推入 `syncQueue` |
| 网络重连 | 消费 `syncQueue` 中的待同步操作，按时间顺序重放 |
| 定时轮询 | `syncInterval` 毫秒后拉取远程变更，与本地合并 |
| 标签点击 | 用户主动下拉同步（显式刷新） |
| App 激活 | 页面从后台切回前台时触发同步 |

## 3. 同步队列设计

### 3.1 同步操作记录

```typescript
interface SyncOperation {
  id?: number;              // 自增主键
  entityType: 'task' | 'list' | 'step';
  entityId: string;
  operation: 'create' | 'update' | 'delete';
  payload: Record<string, unknown>; // 操作时的完整实体快照
  createdAt: string;        // 操作发生时间（用于因果排序）
  retryCount: number;       // 重试次数
  status: 'pending' | 'syncing' | 'failed';
}
```

### 3.2 同步流程

```
1. 用户操作 → 写入 IndexedDB（乐观更新 UI）
2. 同时写入 syncQueue，status='pending'
3. 后台 worker 消费队列：
   ├── 发送 REST 请求
   ├── 成功 → 删除队列记录，更新本地数据的 syncVersion
   ├── 失败 → retryCount++，指数退避重试（最多 5 次）
   └── 网络不可用 → 保留在队列，网络恢复后继续
4. 定期轮询远程：
   ├── GET /tasks?since={lastSyncTimestamp}
   ├── 遍历变更，与本地合并
   └── 更新 lastSyncTimestamp
```

### 3.3 轮询 vs WebSocket

| 方案 | 优势 | 劣势 | 推荐场景 |
|------|------|------|---------|
| HTTP 轮询 | 实现简单，无需后端改造 | 延迟高，有无效请求 | 初期实现 |
| WebSocket | 实时推送，低延迟 | 后端需改造，连接维护复杂 | 多设备实时协作 |

**分阶段实施**：

- **Phase 1**：HTTP 轮询（当前后端已支持 `/health` 等端点，可复用）
- **Phase 2**：WebSocket 推送（需后端新增 WebSocket 支持）

## 4. 冲突解决

### 4.1 冲突场景

两个设备离线期间修改了同一任务的不同字段，或同一字段的不同值。

| 场景 | 示例 |
|------|------|
| 字段级冲突 | 设备 A 修改标题，设备 B 修改截止日期 |
| 状态冲突 | 设备 A 标记完成，设备 B 删除任务 |
| 循环冲突 | 设备 A→B→A 循环修改同一字段 |

### 4.2 冲突策略

#### 策略一：本地优先（默认）

```
规则：
- 本地变更直接生效，忽略远程变更
- 远程变更在下一次同步时覆盖本地（不保留远程变更历史）
```

适用场景：单人使用、多设备但强信任本地数据的用户。

#### 策略二：远程优先

```
规则：
- 远程变更直接生效
- 本地待同步队列中的操作降级为"建议"，通知用户确认
```

适用场景：多设备强一致性优先。

#### 策略三：手动合并

```
规则：
- 检测到冲突时，暂停自动同步
- 弹出冲突解决 UI：
  ├── "使用本地版本"
  ├── "使用远程版本"
  └── "手动合并"（进入编辑模式）
```

适用场景：任务包含重要数据，用户需要掌控。

### 4.3 版本向量

为支持冲突检测，实体增加版本字段：

```typescript
interface Task {
  id: string;
  // ... 其他字段
  version: number;      // 单调递增版本号
  lastSyncedAt: string; // 最后同步时间
}
```

**冲突检测逻辑**：

```
同步时：
1. 拉取远程任务的 version
2. 对比本地 version：
   - remote.version > local.version：远程更新，直接覆盖本地
   - remote.version == local.version：无冲突，合并字段变更
   - remote.version < local.version：本地更新，推送至远程
3. 字段级合并：两个变更修改不同字段 → 自动合并
               两个变更修改同一字段 → 按冲突策略处理
```

## 5. 数据迁移

### 5.1 本地到远程迁移

用户首次登录账号时，需要将本地积累的数据迁移到服务器。

```
┌──────────────────────────────────────────────────────────┐
│                   迁移向导（首次登录时触发）                │
│                                                          │
│  ┌──────────────┐   ┌──────────────┐   ┌────────────┐  │
│  │  检测到本地   │ → │  询问用户     │ → │  执行迁移   │  │
│  │  有数据       │   │  迁移或清空   │   │  合并到账号  │  │
│  └──────────────┘   └──────────────┘   └────────────┘  │
└──────────────────────────────────────────────────────────┘
```

**迁移选项**：

| 选项 | 行为 |
|------|------|
| 合并 | 本地任务 + 清单全部以 `userId` 关联写入远程 |
| 仅保留云端 | 清空本地，以远程数据为准 |
| 不迁移 | 退出账号后本地数据保留，下次登录再问 |

**合并策略**：

- `listId` 为 null 的任务 → 迁移到默认清单
- 清单标题冲突 → 在标题后追加 " (本地)"
- 重复任务判断：按 `title` + `createdAt` 模糊匹配去重

### 5.2 远程到本地迁移

切换到 local 模式时，远程数据全部保留在服务器，不影响。

## 6. 存储模式切换

```typescript
// 切换存储模式
async function switchStorageMode(config: StorageConfig) {
  // 1. 暂停所有同步操作
  await pauseSync();

  // 2. 关闭当前存储连接
  await currentStorage.destroy();

  // 3. 初始化新存储
  const newStorage = config.mode === 'local'
    ? createLocalStorage(config)
    : createRemoteStorage(config);
  await newStorage.initialize();

  // 4. 如果切换到 remote，同步远程数据到本地
  if (config.mode === 'remote') {
    await syncRemoteToLocal(newStorage);
  }

  // 5. 更新全局 storage 实例
  setGlobalStorage(newStorage);

  // 6. 保存配置到 localStorage
  localStorage.setItem('storage-config', JSON.stringify(config));
}
```

## 7. 各平台存储适配

| 平台 | 本地存储 | 文件存储 | 特殊考虑 |
|------|---------|---------|---------|
| **Web** | IndexedDB (Dexie.js) | IndexedDB / OPFS | Service Worker 离线缓存 |
| **Browser Ext** | chrome.storage.local | chrome.storage.local | 独立的存储空间 |
| **Desktop** | IndexedDB | Tauri fs API | 可访问本地文件系统 |
| **Mobile** | AsyncStorage / MMKV | 沙盒文件系统 | iOS Keychain 存 Token |
| **Miniprogram** | wx.setStorageSync | 微信云存储 | 无 IndexedDB |

## 8. 关键实现注意事项

1. **乐观更新**：用户操作立即反映在 UI，失败时回滚（React Query `onMutate` / `onError` / `onSettled`）
2. **幂等性**：同步操作使用实体 UUID 而非自增 ID，支持重放
3. **原子性**：IndexedDB 事务保证本地写入的原子性
4. **防抖**：频繁操作（如输入打字）需要防抖后再写入本地
5. **压缩**：大量任务数据可考虑 LZ-string 压缩后存储
